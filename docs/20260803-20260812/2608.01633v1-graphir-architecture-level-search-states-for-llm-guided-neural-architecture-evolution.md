## 摘要
大语言模型（LLM）使得神经架构搜索（NAS）能够直接在可执行的神经网络程序上进行。然而，代码级别的灵活性并未提供有效变异所需的架构状态：LLM必须从实现细节中推断张量依赖、可编辑组件和兼容性约束。为解决这一表示不匹配问题，我们提出GraphIR，一种架构感知的中间表示，它用对齐变异的候选状态补充可执行程序。GraphIR通过三个互补视图组织每个候选：描述张量流的计算骨架、暴露可编辑模块和操作的变异面，以及捕获接口契约、传播形状和下游依赖的有效性包络。为评估我们的方法，我们构建了NAS-Dependency，一个包含120个问题的基准，覆盖六个互补的依赖推理维度。诊断结果表明，GraphIR在识别精确生产者出现、追踪依赖传播以及诊断接口和失败风险方面特别有效。在包括CLRS在内的六个下游基准上，GraphIR实现了最佳的整体搜索性能，同时在与OpenEvolve集成时保持了相当的模型大小和有利的端到端NAS效率。这些结果表明，面向变异的架构状态为可执行神经程序与LLM引导的架构演化之间提供了有效接口。

## Abstract
Large language models (LLMs) enable neural architecture search (NAS) directly over executable neural network programs. However, code-level flexibility does not provide the architecture state needed for effective mutation: LLMs must infer tensor dependencies, editable components, and compatibility constraints from implementation details. To address this representation mismatch, we propose GraphIR, an architecture-aware intermediate representation that supplements executable programs with a mutation-aligned candidate state. GraphIR organizes each candidate through three complementary views: a computation skeleton describing tensor flow, a mutation surface exposing editable modules and operations, and a validity envelope capturing interface contracts, propagated shapes, and downstream dependencies. To evaluate our method, we construct NAS-Dependency, a 120-question benchmark covering six complementary dependency-reasoning dimensions. The diagnostic shows that GraphIR is particularly effective at identifying exact producer occurrences, tracing dependency propagation, and diagnosing interface and failure risks. Across six downstream benchmarks including CLRS, GraphIR achieves the best overall search performance while maintaining comparable model size and favorable end-to-end NAS efficiency when integrated into OpenEvolve. These results show that a mutation-oriented architecture state provides an effective interface between executable neural programs and LLM-guided architecture evolution.

- 传统 NAS 方法依赖**预定义的架构表示**（如细胞图、操作集、架构语法），这类表示提供了类型化编辑选项、有效性约束和清晰的变异语义，但**限定了搜索空间**，难以探索开放式架构。
- 近年来基于大语言模型（LLM）的 NAS 方法允许直接在**可执行神经网络程序**（如 PyTorch 代码）上进行开放式编辑，极大地扩展了搜索空间。
- 但是，**代码级灵活性并不等于有效的架构搜索状态**：可执行代码是为执行而非为变异设计的，它交织了架构决策与实现细节（变量名、辅助函数、张量重塑等），导致 LLM 必须从实现细节中**自行推断**张量依赖、可编辑组件和兼容性约束，才能提出正确的变异。
- 这种 **“表示不匹配”** 是本文的核心问题：候选的架构状态在源代码中是**隐式**的，LLM 难以有效识别变异目标与依赖关系，从而产生语法有效但架构不一致的候选（例如张量形状不兼容、输出接口被破坏）。
- 该问题的本质是：**在 LLM 引导的代码级架构搜索中，应当向 LLM 提供什么样的候选状态？** 本文的回答是：一个**变异对齐（mutation-aligned）的架构级中间表示**。

## 2. 方法论

### 2.1 核心思想

提出 **GraphIR（Graph-based Intermediate Representation）**，一种架构感知的中间表示，它补充可执行程序，不取代源代码。源代码仍是可编辑和可执行的搜索对象，GraphIR 作为附加的结构化证据，为 LLM 提供变异所需的显式架构信息。

### 2.2 三个互补视图

| 视图 | 表示字段 | 作用 |
|------|----------|------|
| **计算骨架** | (M, T, E) | 描述张量流和主要张量变换的排序 |
| **变异表面** | (M, T, F) | 暴露可编辑模块、操作和结构属性，作为变异目标 |
| **有效性包络** | (I, O, E) | 记录外部接口契约、张量形状、维度耦合和下游依赖，确保变异后的有效性 |

其中 M = 架构模块集合，T = 架构相关张量操作集合，F = 确定性结构事实，E = 生产者-消费者依赖集合，I/O = 输入/输出接口契约。

### 2.3 关键技术细节

- **输入/输出契约构造（两阶段）**：
  1. 通过确定性源码模式对候选分类（如图形处理器工厂或特征组合 → 图结构契约；默认 → 通用 PyTorch 契约）。
  2. 实例化候选，合成轻量示例输入，使用 **PyTorch FX 符号追踪**恢复计算图并做形状传播；若观察到实际输入输出形状，则替换默认契约。

- **模块集合 M 与操作集合 T 的提取**：利用 Python AST 分析可编辑程序区域，将构造函数调用与固定神经网络模块词汇表匹配（线性、卷积、归一化、循环、注意力、正则化、池化等）；将函数调用、张量方法与固定操作词汇表匹配（激活、形状变换、拼接、堆叠、归约、掩码、矩阵乘法等）。

- **结构事实 F 的生成**：通过固定的“触发器→标签”规则（而非 LLM 摘要）生成，包含源码级规则与执行级（FX 图）规则，合并去重。例如：卷积模块 → “卷积/局部混合”事实；显式加法 → “加性融合”事实。

- **依赖集合 E 的生成**：优先采用 FX 图生产者-消费者边；若不可用，退化为静态赋值级依赖（排除模块构造函数依赖和非张量属性初始化以减少虚假边）。

- **渲染与序列化**：固定字段顺序（输入契约、输出契约、模块、张量操作、结构事实、架构图边），过滤查找/索引节点，限制实体数以保持上下文紧凑。节点形状元数据和 profile 标签为内部使用，不显式输出。

### 2.4 算法流程（Algorithm 1 文字描述）

1. 选择标记的进化区域，或使用完整程序。
2. 初始化 profile 特定的契约 I 和 O。
3. 提取 M、T、静态事实 Fs 和静态依赖 D。
4. 实例化候选，合成示例输入。
5. 通过符号追踪和形状传播恢复 FX 依赖 Efx 与观察到的契约。
6. 用观察到的契约修正 I 和 O。
7. 生成执行级事实 Fe。
8. 设置 E ← Efx（若可用），否则 E ← D。
9. 设置 F ← Dedup(Fs ∪ Fe)。
10. 组装并渲染 GraphIR 状态 G(P) 和上下文 C(P)。

### 2.5 变异流程

- 变异提示包含：**源程序 + GraphIR 状态 + 评估历史**。默认按“代码在前、GraphIR 在后”排列，源代码为编辑锚。
- GraphIR 不限制变异类型（模块类型、隐藏维度、分支、张量变换、残差路径等均可修改），不施加预定义架构语法或固定变异算子。
- 子程序生成后，重新为该子程序构建 GraphIR，使新引入的模块、依赖等进入后续迭代。

## 6. 主要结论与发现

- **表示不匹配是代码型 LLM-NAS 的核心瓶颈**：可执行代码支持开放式变异，但未显式暴露变异所需的架构状态。
- **GraphIR 有效解决该瓶颈**：通过计算骨架、变异表面和有效性包络三个互补视图，将隐式架构状态显式化，使 LLM 能够：
  - 更好地定位精确生产者（producer occurrence）；
  - 追踪依赖传播路径；
  - 识别接口与失效风险。
- **推理优势可转化为搜索性能优势**：在 6 个下游基准（含 30 任务 CLRS）上，GraphIR 取得最佳或并列最佳搜索性能，同时保持相当的模型大小和更优的端到端 NAS 效率。
- **变异对齐的架构状态是有效接口**：为可执行神经程序与 LLM 引导的架构演化之间提供了实用、高效的连接。

## 7. 优点

- **问题定位精准**：清晰识别了代码级 NAS 的“表示不匹配”这一未被充分研究的问题，具有理论价值。
- **方法设计合理**：
  - 保留源代码为编辑锚，GraphIR 作为补充，既保持开放性又不失结构性；
  - 三视图分解（骨架/表面/包络）直接对齐变异需求（改什么、怎么改、不能破坏什么）；
  - 状态构造完全基于确定性规则（AST + FX 追踪 + 固定模板），无 LLM 参与，保证可复现性和一致性。
- **构建了专门的诊断基准 NAS-Dependency**：该基准从真实演化轨迹生成，问题类型覆盖六大依赖推理维度，为后续研究提供了评估工具。
- **实验规范**：大部分对比在受控条件下进行（仅替换表示），消融分析清晰，区分了“表示有效性”与“搜索有效性”两个层面。
- **效率优势明显**：相比 CPG-style、GraphCode-style 等结构化表示方法，GraphIR 端到端耗时更低，实用性更强。

## 8. 不足与局限

- **LLM 泛化性未知**：所有实验只用了 Qwen3-Plus，未测试不同 LLM（如 GPT、Claude、Llama 等）下 GraphIR 的稳健性。
- **NAS-Dependency 基准覆盖面窄**：仅由单一搜索设置（MNIST1D-Shuffle CNN）的演化轨迹生成，可能不全面代表所有 NAS 场景；问题规模（120 题）也相对较小。
- **依赖 FX 追踪的可行性**：GraphIR 优先使用可执行追踪（FX），但对无法实例化的程序（如需要特殊外部依赖或动态控制流）会退化为静态分析，效果差异未在实验中单独评估。
- **输入契约推断的限定条件**：输入宽度不能推断时使用预定义特征宽度，这种 fallback 机制可能在实际任务中引入偏差。
- **CLRS 对比的公平性**：部分对比方法结果取自原论文（非同一环境重跑），跨论文比较存在环境差异风险。
- **消融范围有限**：未测试 GraphIR 与更大搜索预算、不同选择策略（如非最佳优先选择）的交互效果。
- **应用边界**：GraphIR 面向 PyTorch 程序，对其他框架（TensorFlow/JAX）或非 Python 代码的迁移性未讨论。
- **理论分析缺失**：文章未从理论上解释为什么变异对齐的表示优于通用代码图，更多依赖实证观察。
